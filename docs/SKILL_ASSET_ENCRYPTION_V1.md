# 技能与知识资产加密交付规范 V1

状态：设计规范，待评审后实施

上位文档：`SKILLPASS_PRODUCT_V1.md` · `AGENT_COMPANY_PROTOCOL_V1.md`

---

## 一、这个规范解决什么

Agent Company Protocol 要求一家 Agent Company 能「**拥有能力**」。当前 V1 只做到
了身份层：链上有一本 Skill Passport，能发 License、能留 Receipt。

**但技能和知识的实现本身没有任何保护，也没有交付机制。**

结果是：所谓「拥有」只是拥有一张产权证。买方拿到的是身份，不是能力；资产内容
躺在链下某台服务器上，谁都能拷。

本规范定义「拥有能力」的完整实现：

```text
资产内容  加密后公开存放，只有买断者能解开
调用权    租用者可以调用服务，但拿不到文档
买断权    拿到足额解密份额 + 链上所有权
转让权    所有权转移时，为买方重新交付份额
```

---

## 二、三层交付模型

| 层级 | 拿到什么 | 能做什么 | 怎么取得 |
| --- | --- | --- | --- |
| **看到** | 公开说明、输入输出定义 | 知道这个技能能干什么 | 打开链上网站 |
| **调用** | 只能调用服务 | 用服务，**拿不到文档** | 买 License，走 Skill Gate |
| **拥有** | **足额解密份额 + 链上所有权** | 看文档、自己跑、改、再卖 | 买断 |

**为什么只有两层付费（调用 / 拥有）**：技术上讲不出「只有解密权、没有转让权」这
一层——重建密钥后就等于拿到内容，就能用、能改、能复制。中间层是假的，不做。

---

## 三、资产的定义

```text
技能/知识资产 =
  ├── 清单哈希      链上记录，证明资产版本没被改
  ├── 密文哈希      写在清单里，证明密文没被改
  ├── 密文          存在容器里，公开可下载
  ├── 解密份额      阈值节点加密给所有者后交付
  ├── 链上所有权    Registry 记录
  └── 附带权利      发许可证、收版税、获得更新、合法调用
```

**「附带权利」才是资产值钱的原因。** 一份纯文档被复制走就没了；但一个技能的文档
被复制走，复制者仍然没有链上权利，仍然不能合法调用服务，也拿不到后续版本。

**这就是本规范选择「卖能力」而不是「卖文件」的理由。**

### 内容存放原则

链上只存**哈希**，密文放在容器里。容器是**其中一个副本**，不是唯一副本：

```text
内容身份 = 哈希（在链上）
内容位置 = 容器（可替换）
```

这样即使容器持有者删了文件，只要哈希还在，内容仍可从别处恢复。

### 可交易资产的范围

V1 不把 `Skill` 限死在一段 Prompt。可交易资产包括：

```text
Skill / Prompt
Workflow / SOP
方法论与经验手册
结构化知识包
数据集或评测集
可复用代码与工具说明
研究资料与引用索引
```

API Key、平台账号、私钥和不可转让的凭证不属于资产内容，也不得写入密文包。
卖家卖的是可复用的知识与能力，不是把自己的账号一起交出去。

### 资产包格式

每个版本是一个可验证的资产包，而不是散落的一堆文件：

```text
manifest.json                                 公开、明文，描述这个版本
content/<asset-id>/<version>.bin              私有内容密文
shares/<skill-id>/<version>/<key_epoch>/      阈值节点份额
pubkeys/<buyer>.json                          买方公钥及归属证明
```

`manifest.json` 至少包含：

```json
{
  "schema": "skillpass.asset.v1",
  "skillPassportId": "0x...",
  "version": "1.0.0",
  "contentPath": "content/...bin",
  "contentSha256": "0x...",
  "contentAlgorithm": "xchacha20-poly1305",
  "publicPreview": "公开说明和输入输出定义"
}
```

`manifest.json` 只允许出现公开信息。价格、买家地址、加密份额和内部笔记不得写进
manifest。

### 链上版本哈希

不为了第一版再部署一个 Registry。现有
`Passport.currentVersionHash` 继续使用，但语义收紧为：

```text
currentVersionHash =
  sha256(UTF-8 canonical JSON bytes of manifest.json)
```

链上哈希证明 Manifest 没有被改；Manifest 里的 `contentSha256` 再证明密文没有被改。
这样不新增合约也能完成「版本 → Manifest → 密文」的完整验证链。

## 四、密钥体系

### 4.1 密码学构成

```text
内容加密      XChaCha20-Poly1305（对称，带完整性校验）
随机内容密钥  K，每个资产版本一份，32 字节
阈值拆分      K -> `t-of-n` 份额，KMS/HSM 独立保存
份额加密      X25519，把每个份额加密给买方公钥
密钥派生      HKDF-SHA256，从钱包签名派生接收方的 X25519 密钥对
```

这套构造沿用 TapeOut DeWÉB 已经验证过的组合（见 `TapeKit/send/module/src/keys.js`），
不自己发明密码学。

### 4.2 买方的密钥从哪来

**普通钱包没有「用私钥解密」这个功能。** 所以解密密钥不能直接用钱包私钥，必须
从**钱包签名**派生：

```text
1. 买方用钱包签一段固定文字（EIP-4361 格式）
2. 签名规范化（低 s）→ 作为 HKDF 的输入密钥材料
3. HKDF-SHA256(材料, salt, info) → 32 字节 X25519 私钥
4. 由私钥算出 X25519 公钥
5. 只把公钥和一份独立的归属证明公开
```

**私钥不落地**——每次需要时由同一个钱包重新签名得到。签名文字是固定的，所以同一
个钱包每次签出的派生结果一致。

**用于派生私钥的原签名必须永久保密。** DeWÉB 自己的签名文字已经写明：
“Anyone who obtains this signature can read your messages.” 因此：

- 原签名只在买方浏览器内存中存在，绝不写容器、日志、分析服务或订单备注；
- 卖家只收到买方公钥，收不到原签名；
- 买方公钥通过一条独立的注册消息签名证明归属；这条公开证明签名不能拿来做密钥派生。

买方在订单中提交公钥和归属证明。卖方验证地址与证明后，把它写入：

```text
pubkeys/<buyer-address>.json
```

内容包括公钥、钱包地址、链 ID、注册消息摘要和公开的归属证明签名。文件只能由
资产容器控制者写入，买方提交的内容不能直接覆盖已有公钥。阈值份额只能加密给这个
买方公钥。

### 4.2.1 支持范围

V1 只支持能稳定执行 EIP-191 `personal_sign` 的钱包。每次签名结果必须一致；如果
钱包每次返回不同签名，或者签名由无法复现的托管/多签流程产生，就不能使用这条密钥
路径。界面必须在签名前做两次确定性检查，并在不合格时停止购买，不能生成一把下次
重建不出正确密钥。

### 4.3 签名文字里的域名（关键约束）

DeWÉB 的参考实现把域名写死为 `www.tapesend.com`：

```js
export const KEY_DOMAIN = 'www.tapesend.com';
```

签名文字的第一行是 `<域名> wants you to sign in...`，钱包会把它和发起请求的网站
比对（EIP-4361 反钓鱼）。**域名不一致时钱包会报警告。**

这带来一个必须决策的分叉：

| | 复用 DeWÉB 密钥 | 自建派生 |
| --- | --- | --- |
| 签名域名 | 必须是 `www.tapesend.com` | 用我们自己的站 |
| 买方门槛 | 必须装 TapeSend 客户端 | **只要有钱包** |
| 能否在我们的站解密 | ❌ 不能 | ✅ 能 |
| 加密实现 | 平台现成 | 沿用同一构造 |
| 依赖 | DeWÉB 中枢（尚未 seal） | 无 |

**建议选「自建派生」**，理由：

1. 买方门槛最低——不需要容器、不需要装额外客户端
2. 全流程留在我们自己的链上网站内完成
3. 密码学构造是抄来的，不是发明的
4. 不依赖一个还没 `seal()` 的合约

**代价**：不能复用 DeWÉB 内置的密钥派生作为我们的买方密钥，否则买方的解密动作会被
绑定到 DeWÉB 站点。我们可以沿用相同密码学构造自建密钥，也可以把 DeWÉB 中枢只当作
可选的份额传输通道。对外必须说清楚，不能把两种能力混成一句。

### 4.4 密钥丢失

私钥不落地 = 只要钱包还在，钥匙就能重新派生出来。**钱包丢了资产就解不开了。**

这一条必须写进用户提示，不能藏。

## 五、份额投递通道

### 5.1 候选通道对比

| 通道 | 优点 | 缺点 |
| --- | --- | --- |
| **DeWÉB 消息**（`0xe61A9C72…`，X Layer 已启用） | 端到端加密、平台原生、可通知 | 签名域名写死、买方需容器、依赖未 seal 的合约 |
| **容器文件** | 用现成的 SiteRegistry、无需新合约 | 每个买方一个文件、内容公开（但已加密） |
| **Registry 字段** | 最直接 | 需要改合约 |
| **链外邮箱** | 便宜 | 引入信任缺口，不做 |

### 5.2 建议方案

```text
每个委员会节点产生一个加密份额包
路径：shares/<技能id>/<版本>/<key_epoch>/<买方地址>/<节点>.share
```

买方读取不少于 `t` 个文件 + 钱包签名 → 本地重建 K → 解开文档。

**与 DeWÉB 的关系**：不能让买方复用 DeWÉB 写死的签名域名。我们使用自己的密钥派生，
但可以把 DeWÉB 当作可选消息通道，发送已经由阈值节点加密给买方公钥的份额包。

份额文件不是裸份额，而是只对买方公钥可解的包：

```text
版本 + 节点 ID + key_epoch + 临时 X25519 公钥 + nonce
+ XChaCha20-Poly1305 密文
附加认证数据 = chainId + 容器 + passportId + version + order + 买方地址
```

同一份份额重复投递必须得到同一语义结果。界面用 `passportId + version + buyer`
做幂等键，不能因为用户刷新页面就重复扣费或反复写链。

### 5.3 交付的自动性

```text
1. 买方注册公钥，在站上点「买断」
2. 买方钱包直接把款项付给站内 Ownership Sale 合约
3. 合约记录买断订单并暂存款项
4. 自动交付引擎监听到订单已付款
5. 阈值节点独立验证付款和订单
6. 节点把加密份额发送给买方
7. Ownership Sale 合约自动转移 Registry 所有权
8. 合约自动把款项结算给卖方
```

第 4 至 8 步全部自动完成。买方不需要再次确认，IMOO 也不是必要执行者；它可以只是
最初的节点运营方之一。

Ownership Sale 合约只处理「资产所有权买断」，不处理 Agent 服务订单。密钥网络在约定
时间内没有达到阈值交付，订单会自动退款。交付成功、所有权转移和放款由合约状态
自动推进，不设置买方确认卡。

**风险**：自动交付仍需要达到阈值数量的托管节点在线。超时退款可以保护买方的款项，
但密钥份额网络是系统必须持续维护的基础设施。

### 5.4 与 OKX.AI 的边界

两条商业路径必须分开，不能共用订单或状态：

| 路径 | 交易内容 | 付款与交付 |
| --- | --- | --- |
| **OKX.AI Service Order** | 雇一个 Agent 执行一次或一段时间服务 | OKX.AI 管理和交付服务结果 |
| **SkillPass Ownership Sale** | 买走 Skill / 知识资产的所有权和解密份额 | SkillPass 站内买断合约 |

调用服务不等于买断资产。买断资产也不产生一次 OKX.AI Job，不写入 `okx_job_id`。
二者可以互相推荐，但订单、退款、评价和 Receipt 必须分开记录。

## 六、所有权与转让

### 6.1 两个所有权是分开的

| 所有权 | 存在哪 | 管什么 |
| --- | --- | --- |
| Passport 所有权 | Trust Registry | 技能身份、发许可证、收版税 |
| Circuit NFT 所有权 | ERC-721 | 电路资产、**它的容器** |

`AGENT_STANDARD_CELL_LIBRARY_V1.md` 已经写明：Circuit 的 ERC-721 所有权**不能自动
等同于全部商业权利**。本规范不改变这条。

### 6.2 转让流程

```text
买方在站内付款到买断合约 → 阈值节点交付加密份额
-> 合约自动放款 → Registry 自动转移所有权
```

**转让不要求原所有者在线**——只要密钥托管网络仍然持有足额的版本份额，节点就可以
为新买方重新加密并交付。原所有者下线不会阻断自动转让。

**V1 的约束**：密钥份额交付和 Registry 写入属于不同交易，因此用买断合约的订单状态
依次约束：付款、阈值交付、放款、所有权转移。所有权只能在达到交付阈值后转移，不会
出现“付了钱但没有任何交付”的直接转账。

**站内不等于零风险**：合约无法独立证明每个加密份额都对应正确内容，只能验证份额
证明、版本哈希和订单条件。恶意交付依靠节点质押、审计和争议机制处理。

**无法撤销的事实**：旧所有者看过内容后，转让不能把知识从它的记忆或存储里收回。
所有权转让只改变链上权利和后续版本权利。若新版本必须与新所有者绑定，应发布新
版本和新内容密钥，不能宣传成“旧所有者已被技术性清除”。

## 七、与现有系统怎么接

| 现有组件 | 变化 |
| --- | --- |
| Skill Gate（Circuit #1） | 不变。继续判断授权 |
| License Quota（Circuit #2） | 不变。继续扣额度 |
| Trust Registry | 增加按 Passport 限定的 Ownership Sale 转移权限；`currentVersionHash` 改指 Manifest 哈希 |
| 容器 / 链上网站 | **加资产文件**，不用新开容器、不用再付费 |
| Ownership Sale 合约 | **新增站内买断状态机**：收款、阈值交付、退款、自动放款 |
| Route & Royalty Core | 从「计划」提升为「下一步」，因为它决定买断收入怎么分 |

加密份额和买方公钥放在容器文件或 DeWEB，不塞进 Registry，避免为了 V1 再部署一套
合约。
Registry 只保留链上权利和版本声明。

不能把 Ownership Sale 合约设为全局 controller，也不能要求 IMOO 在执行路径中调用
`transferPassportOwnership`。Registry 需要增加按 Passport 限定的转移权限：只有该
资产绑定的 Ownership Sale 合约，在达到阈值交付后，才能把对应 Passport 转给买方。

| 需求 | 用什么 | 现状 |
| --- | --- | --- |
| 存密文 | SiteRegistry（24,000 字节/块，带 SHA-256） | ✅ 已在用 |
| 公开入口 | 链上名字 + 网关（`1.2.223.tape`） | ✅ 已上线 |
| 站内买断收款 | Ownership Sale 合约暂存，阈值交付后自动放款 | 🟡 待开发 |

| 站点持久化 | localStorage / IndexedDB，按容器隔离 | ✅ 规范允许 |

## 九、安全边界与已知限制

必须如实写，不允许美化。

1. **买断者解密后可以复制，密码学上防不住。**
   防住的是：租用者偷看、传输截获、平台偷看。防不住的是：买方自己转发。
   这靠信誉和法律，不靠密码学。

2. **阈值节点必须在线响应交付。**
   如果在线节点不足阈值，买方无法重建密钥。
   缓解：买断合约设置交付期限，超时后买方可以取回款项。

3. **容器不是保险箱。**
   持有电路 NFT 的人可以删除容器里的文件。因此内容身份以**链上哈希**为准，容器只
   是其中一个副本。

4. **钱包丢失 = 资产永久锁死。**
   密钥由钱包签名派生，钱包没了就解不开。

5. **钱包签名能力有限。**
   非确定性签名钱包、部分多签钱包和无法稳定复现 `personal_sign` 的钱包不支持 V1。

6. **DeWÉB 中枢尚未 `seal()`。**
   在封印之前，其 owner 可以更换实现。这是平台层面的风险，本规范不依赖它。

7. **「100% 链上」徽章**需要站点不引用链外资源。当前站点在运行时调用 X Layer RPC
   节点（规范允许），静态 HTML 里没有链外引用。是否符合徽章条件，以网关状态页
   `/.tape/status` 的判定为准。

## 十、V1 范围

**做：**

- 技能/知识内容加密，密文存进容器
- 资产 Manifest 哈希上链
- 买方公钥从钱包签名派生
- 阈值份额加密后写入容器
- 站内解密页
- 站内买断流程（付款 → 自动交付份额 → 自动转移所有权）
- Ownership Sale 合约及超时退款、重复交付保护
- Trust Registry 的按 Passport 限定转移权限

**不做：**

- 通用 Agent 服务市场（OKX.AI 负责）
- 与 OKX.AI 共用服务订单来承载资产买断
- 动态投资和复杂分账（V2 之后）
- 资产的转出与提现（X Layer 当前不支持，**不宣传**）
- 复用 DeWÉB 内置密钥派生（见 §4.3；DeWÉB 只能作为可选传输通道）

### 验收条件

第一版至少通过以下测试：

1. 同一钱包两次派生出的公钥完全一致；
2. 正确买方能用钱包签名解开不少于 `t` 个份额并重建 K；
3. 非买方地址不能解开份额；
4. 密文或 Manifest 被改动一个字节后，完整性校验失败；
5. 同一订单重复交付不会重复收款、重复转移所有权或覆盖份额；
6. 交付失败的订单不会转移所有权，并会自动退款；
7. 新版本使用新内容密钥，旧版本份额不能重建新版本密钥；
8. 解密后的明文只存在内存，刷新页面后消失；
9. 买断订单完成后，款项只释放一次，所有权只转移一次；
10. 卖方超时未交付，买方可以取回款项。

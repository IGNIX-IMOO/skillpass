## 一、目标

为 SkillPass Ownership Sale 提供自动、可扩展、可迁移的密钥托管网络：

- 任意合格的节点运营方可以申请加入；
- 节点可以质押多种代币；
- 每个技能只交给随机委员会保管，而不是全网每个节点；
- 使用 `t-of-n` 阈值交付，不依赖 IMOO 或单一服务器；
- 买方付款后自动交付，不需要买方再次确认；
- 节点按实际存储、验证和交付工作获得服务费；
- 节点运营方可以从 IMOO 逐步迁移到 IGNIX、OKX、第三方或社区节点。

这不是一个新的通用区块链，也不是新的 Agent 服务市场。它是 SkillPass 资产买断流程
下面的密钥托管和自动交付网络。

## 二、核心原则

```text
一个技能版本      一个独立内容密钥 K
一个内容密钥      一组可验证阈值份额
一个资产委员会    由多个独立运营节点组成
一个节点          不保存所有资产的全部份额
一个买方订单      只能对应一组有效交付
一个节点运营方    不能靠注册大量节点控制委员会
```

IMOO 可以是最初的节点运营方之一，但不能是永久唯一控制者。

## 三、网络角色

| 角色 | 职责 |
| --- | --- |
| Skill Seller | 创建资产、生成内容密钥、提交份额 |
| Asset Buyer | 提供解密公钥、付款、在本地重建密钥 |
| Ownership Sale | 收款、订单状态、退款、所有权和放款 |
| Node Operator | 运行一个或多个托管节点 |
| Custodian Node | 保存份额、验证订单、发送加密份额 |
| Standby Node | 不参与当前委员会，但可替换故障节点 |
| Committee | 为某个资产版本服务的一组节点 |
| Stake Vault | 保存多代币质押和解除质押状态 |
| Risk Oracle | 提供代币价格、流动性和风险参数 |
| Governance | 管理代币准入、阈值、费率、惩罚和升级 |
| Insurance Pool | 覆盖可证明事故或协议补偿 |

## 四、节点生命周期

```text
APPLYING
-> VERIFIED
-> STAKED
-> CANDIDATE
-> ACTIVE
-> STANDBY
-> EXITING
-> EXITED
```

节点申请时需要提交：

```text
operator_id
node_public_key
endpoint
supported_chains
kms_or_hsm_attestation
region
uptime_commitment
security_contact
stake_positions[]
```

申请通过不等于自动进入所有委员会。节点先成为候选者，再由委员会选择算法选出。

## 五、多代币质押

### 5.1 为什么不直接按代币数量计算

不同代币的 decimals、价格、流动性和风险不同，不能直接相加：

```text
1 IMOO != 1 OKB != 1 USDT != 1 其他项目币
```

网络必须计算统一的 `Effective Stake`，而不是代币数量。

### 5.2 代币准入

“支持多种代币”不等于任何代币都能立即成为有效质押。每个代币先进入 Token Registry：

```text
token_address
chain_id
decimals
oracle_source
liquidity_score
risk_tier
haircut
global_cap
operator_cap
unbonding_period
slash_adapter
```

治理可以开放申请，但至少检查：

- 合约是否可暂停、增发、黑名单或任意修改余额；
- 是否有可靠价格来源；
- 是否有足够流动性和交易深度；
- 是否存在 fee-on-transfer、rebasing 或恶意回调；
- 持币是否高度集中；
- 项目方是否能无限铸造；
- 代币与节点、技能资产是否高度关联。

恶意或无法可靠估值的代币不能作为有效质押。

### 5.3 风险分层

建议分为：

| 层级 | 示例 | 用途 |
| --- | --- | --- |
| A | OKB、主流稳定币 | 基础质押，最高权重 |
| B | IMOO、成熟高流动性代币 | 补充质押，有限权重 |
| C | 合作项目方代币 | 只能作为附加质押 |
| D | 低流动性、可无限增发或高风险代币 | 不接受 |

### 5.4 有效质押计算

```text
raw_value =
  token_amount * oracle_price

risk_adjusted_value =
  raw_value
  * haircut
  * liquidity_factor
  * volatility_factor

effective_position =
  min(risk_adjusted_value, token_global_cap)

operator_effective_stake =
  min(sum(uncorrelated effective_position), operator_weight_cap)
```

默认规则建议：

- 节点必须保持至少 `10,000 SU` 的 A 层基础质押；
- B 层和 C 层代币最多占选择权重的 50%，不能替代基础质押；
- 单一项目币不能贡献超过节点权重的一定比例；
- 同一个项目方发行的多个代币要合并计算关联风险；
- 一个运营方不能获得全网有效权重的绝对多数；
- 价格下跌后，节点需要在宽限期内补仓。

具体比例由治理参数决定，不在本规范中写死。

### 5.5 质押头寸

一个节点可以同时持有多个质押头寸：

```text
stake_position_id
node_id
token
amount
effective_value_snapshot
risk_tier
staked_at
unbonding_start
status
```

被质押代币不能被再次借出、重复质押或自由转走。

### 5.6 价格变化

节点权重不能使用瞬时价格。系统应使用：

```text
多源价格
时间加权平均价格
异常价格熔断
低流动性折扣
纪元快照
```

价格预言机失败时，代币权重只能降低或冻结，不能自动提高。

## 六、委员会与阈值

### 6.1 参数

```text
committee_size = n
threshold = t
```

建议阶段：

```text
启动期：2-of-3
标准期：6-of-9
高价值资产：8-of-11
```

委员会数量可以扩大，但每个资产只需要一个固定大小的活跃委员会。

### 6.2 资产风险等级

| 资产等级 | 建议委员会 | 建议阈值 |
| --- | --- | --- |
| 低价值测试资产 | 3 | 2 |
| 标准资产 | 9 | 6 |
| 高价值资产 | 11 | 8 |

资产价值越高，委员会和阈值越高。卖方也可以在发布时主动选择更高安全等级。

### 6.3 委员会选择

```text
候选池
-> 去掉离线和高风险节点
-> 计算运营方有效权重
-> 应用单运营方上限
-> 使用可验证随机数选择
-> 组成委员会和候补节点
```

选择不能只按质押量排序，否则大额质押者可以长期垄断。随机性、信誉、在线率和独立
运营方去重都必须参与。

### 6.4 候补节点

每个委员会要配置候补节点。正式节点退出或长时间不可用时，由候补节点参与份额迁移。
候补节点只能获得较低待命奖励，不参与正常解密。

## 七、资产密钥生命周期

### 7.1 创建资产版本

```text
1. 卖方为版本生成随机内容密钥 K
2. 使用 K 加密技能或知识内容
3. 为 K 生成可验证的 2-of-3 或 t-of-n 份额
4. 每个委员会节点只收到自己的份额
5. 链上记录份额承诺和 key_epoch
6. 节点将份额保存到 KMS 或 HSM
```

正常流程中，创建者、节点和交付引擎都不应该看到完整 K 在服务器中落盘。

### 7.2 密钥纪元

每次节点集合或安全策略变化，都增加密钥纪元：

```text
key_epoch_id
asset_version
committee_id
threshold
commitment_hash
created_at
retired_at
```

买方订单必须绑定明确的 `key_epoch_id`，不能只写技能 ID。

### 7.3 新节点加入

新节点可以：

- 参与以后创建的资产；
- 通过阈值份额重分发参与旧资产；
- 在旧资产重新加密后参与新版本。

新节点不能因为加入网络就自动获得以前所有资产的份额。

### 7.4 节点退出

退出需要经历：

```text
停止接收新资产
-> 完成未结交付
-> 等待 unbonding
-> 迁移或销毁份额
-> 解除质押
```

如果节点曾经掌握过足够份额恢复旧 K，退出无法证明它已经忘记。高价值旧资产需要
重分发或重新加密。

## 八、自动买断和交付

### 8.1 正常流程

```text
1. 买方注册解密公钥
2. 买方在站内付款到 Ownership Sale
3. 付款达到最终确认
4. 每个节点独立验证订单
5. 达到不少于 t 个节点发送加密份额
6. 节点向合约提交交付证明
7. 合约自动放款并转移所有权
8. 买方在本地合并份额得到 K
```

买方不需要再次确认，IMOO 不在正常执行路径中。

### 8.2 节点独立验证

每个节点都要自己确认：

```text
order_id 存在
payment_final = true
asset_version 正确
key_epoch 正确
buyer_public_key_hash 正确
订单未退款、未取消、未重复交付
```

节点不能只相信中心化交付引擎传来的状态。

### 8.3 交付证明

节点将加密份额发给买方后，向合约提交：

```text
delivery_attestation =
  order_id
  asset_version
  key_epoch
  committee_id
  buyer_public_key_hash
  encrypted_share_hash
  node_id
  signature
```

合约统计唯一且有效的委员会节点签名。达到阈值后自动完成结算。

### 8.4 两种投递通道

| 买方类型 | 主通道 | 备用通道 |
| --- | --- | --- |
| 拥有 TapeOut 容器 | DeWEB | 加密文件 |
| 只有普通钱包 | 加密文件 | 页面订单查询 |

份额本身已经对买方公钥加密，所以两种通道都不会泄露 K。

## 九、奖励

### 9.1 收费来源

```text
买断成交服务费
份额持续存储费
节点验证费
高价值资产安全费
协议维护预算
```

一次买断费不能承担永久存储成本。每个资产还应配置密钥托管储备金或周期性维护费。

### 9.2 奖励分配

建议先采用以下结构，比例由治理配置：

```text
参与交付的委员会节点
待命节点
保险池
持续存储基金
协议治理基金
```

分配依据包括：

- 有效质押；
- 实际参与份额；
- 在线率；
- 历史交付成功率；
- 资产风险等级；
- 存储时长；
- 是否参与故障恢复。

只质押但长期不在线，不能获得完整交付奖励。

### 9.3 奖励结算

结算需要固定纪元，不能在价格波动后重算历史：

```text
epoch_id
reward_pool
eligible_nodes
effective_stake_snapshot
delivery_score
reward_amount
```

奖励可以按原付款代币结算，也可以进入统一奖励池后再分配。两种模式必须择一，不能
让节点自行选择有利价格。

## 十、惩罚与保险

### 10.1 可证明违规

以下行为可以触发罚没：

- 长期离线；
- 拒绝参与已批准交付；
- 提交无效份额；
- 对同一订单提交矛盾结果；
- 使用错误资产版本；
- 重复发送不同份额；
- 伪造在线证明；
- 违反节点升级和密钥策略。

### 10.2 难以证明的风险

节点偷偷复制份额或与买方串通，通常无法从链上自动证明。因此需要：

- 独立审计；
- 保险池；
- 节点信誉；
- 高价值资产更小委员会加更高阈值；
- 定期密钥重分发；
- 节点运营方身份约束；
- 资产价值上限。

不能宣传成“质押自动保证节点绝不泄露”。

### 10.3 惩罚顺序

```text
警告
-> 降低权重
-> 暂停委员会资格
-> 罚没部分质押
-> 强制退出
-> 保险理赔
```

惩罚必须可复核，不能由单一管理员任意决定。

## 十一、治理

V1 建议采用分层治理：

```text
技术参数：平台安全委员会
代币准入：风险委员会
高价值争议：多方仲裁
节点和代币参数：链上参数注册表
```

治理控制：

```text
接受的质押代币
风险层级和 haircut
单代币和单运营方上限
委员会大小和阈值
服务费率
惩罚范围
解除质押周期
节点软件版本
```

治理变更必须延迟生效，并公开原因和影响范围。

## 十二、迁移路径

```text
阶段 0
IMOO 运行 2-of-3
只做内部和低价值资产

阶段 1
IMOO、IGNIX、第三方各控制一个节点
形成真实 2-of-3

阶段 2
开放多代币质押和候选节点
使用 6-of-9 委员会

阶段 3
开放节点运营方轮换
使用 8-of-11 高价值委员会
```

从阶段 0 开始，每个份额都必须带节点身份和 key epoch。以后迁移不能重写历史，只能
增加新纪元或发布新版本。

## 十三、安全边界

必须明确：

1. 多数节点合谋仍可能恢复 K。
2. 质押不能证明节点没有复制份额。
3. 项目方代币可能快速贬值，不能单独提供安全。
4. 价格预言机失败会影响权重。
5. 节点长期退出可能导致旧份额不足阈值。
6. 历史已泄露的 K 无法追溯收回。
7. 买方解密后仍可以复制或转发。
8. 私钥钱包丢失后，买方通常无法恢复资产。
9. 节点网络只能降低单点风险，不能保证绝对安全。

## 十四、V1 验收条件

1. 节点可以质押至少三种测试代币；
2. 不同代币按有效价值计算，不能直接按数量相加；
3. 单一运营方不能靠注册大量节点占据委员会多数；
4. `2-of-3` 中任意一个节点离线仍可交付；
5. 一个节点不能恢复完整 K；
6. 达到阈值后买断自动完成，不需要买方确认；
7. 节点未达到交付阈值时自动退款；
8. 重复订单不会生成第二套有效份额；
9. 代币价格下跌后节点会被要求补仓或降低权重；
10. 节点退出后，新资产使用新的 key epoch；
11. 旧资产可以安全迁移或重新加密；
12. 正常买断流程中 IMOO 不是必要条件。

## 十五、参数基线

V1 默认参数集中在 `KEY_CUSTODY_PARAMETERS_V1.md`：

```text
启动 2-of-3
标准 6-of-9
高价值 8-of-11
基础安全质押 10,000 SU
单运营方上限 10%
网络服务费 1.0%
解除质押 30 days
参数治理 3-of-5 + 72h timelock
```

这些参数是待评审的 V1 默认值，不写入不可升级合约。
